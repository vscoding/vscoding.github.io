Coding

编码能力的提升，不只是掌握更多语法或框架，而是逐步形成描述问题、选择工具、抽象场景、理解约束并构造可持续演进系统的能力。

一、编码能力的五个阶段

这五个阶段描述的是关注点的变化，不是严格的等级。进入新的语言、生态或业务领域时，即使经验丰富，也可能重新经历前几个阶段。

第一阶段：掌握语言

这一阶段关注语言的基本语法、类型系统、控制结构、标准库和工具链。目标不是记住所有语法，而是能够准确判断代码表达了什么、运行时会发生什么，以及错误出现在哪一层。

学习结果应当表现为稳定的基础能力：能够实现需求、阅读错误信息、编写测试，并使用语言自身提供的方式组织代码。

第二阶段：使用生态解决问题

掌握语言之后，关注点转向包管理、框架、构建工具、调试工具和社区惯例。面对问题时，先判断生态中是否已有成熟方案，再比较不同方案在当前环境下的适用性。

这里的“相对最优”不是寻找抽象意义上的最佳工具，而是在功能、复杂度、维护成本、性能和团队能力之间做出可解释的选择。

第三阶段：从生态中提取抽象

反复使用生态中的框架和工具后，需要进一步理解它们为什么这样设计。不同实现往往在重复处理相似的问题，例如资源生命周期、状态管理、扩展机制、错误传播和并发协调。

这一阶段的重点，是从具体 API 中总结出场景中的对象、关系和方法，并能够把这些抽象迁移到新的问题中。

第四阶段：用语言特性描述问题

编程语言的意义不仅是执行指令，也是提供一套描述问题的能力。类型、内存模型、并发模型、元编程能力和运行时机制，会影响哪些设计容易表达、哪些约束能够被静态检查，以及哪些成本必须留到运行时承担。

可以沿着两条路径继续深入：

  • 从语言自身的特性，理解生态中常见设计为何形成。

  • 从问题的结构出发，选择更适合该语言表达能力的实现。

语言特性会约束和支持生态，但不会单独决定生态。工程传统、运行环境和历史兼容性同样会影响最终设计。基于语言本身的性能优化，也属于这一阶段。

第五阶段：构造可迭代的生态

更高层次的目标不是完成一个孤立系统，而是构造能够持续迭代的生态：不断丰富底层能力，提升上层表达能力，同时优化连接底层与上层的工具、协议和过程。

这种生态应当形成可验证的反馈循环：

  1. 底层能力支持上层解决更复杂的问题。

  2. 上层实践暴露底层抽象的缺口。

  3. 中间层把重复经验沉淀为稳定接口和工具。

  4. 新能力反过来用于改进生态自身。

Dogfooding 是重要原则：系统应尽可能使用自身提供的能力完成构建、测试、发布和演进。但自用不等于正确，仍然需要真实用户、运行数据和外部约束提供反馈。

二、阅读框架源码的目标

阅读框架源码时，最容易陷入的误区是过早深究某个实现细节。源码阅读的首要目标不是理解每一行代码，而是理解框架完成目标功能的过程。

可以先把框架看成一个函数：

O = F(I, C, S)

其中：

  • I （Input）表示外部输入，例如请求、事件或用户调用。

  • C （Context）表示配置、依赖和运行环境。

  • S （State）表示框架读取或维护的状态。

  • O （Output）表示返回值、副作用、状态变化和对外事件。

这只是用于阅读的工程模型，不表示框架一定是无状态的纯函数。它的作用是先明确边界，再进入内部实现。

一次有效的源码阅读，至少应当回答以下问题：

  • 框架解决什么问题，不解决什么问题？

  • 输入从哪里进入，结果从哪里离开？

  • 主流程由哪些关键结构协作完成？

  • 状态在哪里产生、保存和变化？

  • 哪些约束始终成立，哪些行为允许扩展？

  • 异常、取消和资源释放如何传播？

三、拆分结构

可以把框架的整体结构称为 overall structure ，把承担局部职责的结构称为 local structure：

overall structure = local structures + relationships + constraints

整体与局部是递归关系

  • 一个 overall structure 由多个 local structure 组成。

  • 一个 local structure 内部仍然可以被视为新的 overall structure。

  • 拆分应当持续到当前问题已经能够被解释，而不是持续到每一行代码。

因此，阅读源码不是简单地从大文件走向小文件，而是在不同抽象层级之间切换。

局部结构不只是一段代码

local structure 可以是类、函数、模块和数据结构，也可以是一个生命周期、协议、回调过程、状态机或设计概念。

同一个对象从不同角度观察，会呈现不同的信息。例如，从生命周期角度关注创建和释放，从并发角度关注共享与隔离，从扩展角度关注接口和注册机制。

关系比目录更重要

局部结构之间为了传递和使用信息而建立关系。这里的“引用”不限于语言层面的对象引用，还包括：

  • 数据流：数据由谁创建、转换和消费。

  • 控制流：谁调用谁，谁决定下一步。

  • 状态流：状态何时变化，由谁维护。

  • 依赖关系：一个结构成立需要哪些外部能力。

  • 扩展关系：用户代码通过什么边界进入框架。

阅读时应优先找到主流程上的关键 local structure 及其关系。理解一个处于关键路径上的局部结构，通常比阅读多个边缘实现更有价值。

四、拆分行为

阅读行为可以概括为一个循环：

猜想 → 验证 → 校正 → 质疑 → 新的猜想

猜想

在进入实现前，先根据公开 API、示例和文档提出假设：

  • 框架如何抽象用户面对的对象和过程？

  • overall structure 可能由哪些 local structure 组成？

  • 局部结构之间可能存在什么关系？

  • 每个局部结构分别承担什么输入、输出和转换职责？

  • 正常路径和失败路径分别如何推进？

猜想的价值是为阅读建立方向，而不是提前得出结论。

验证与校正

沿着入口、测试、日志或调试路径进入实现，确认调用关系、状态变化和边界条件。如果实现与猜想不同，就修改整体模型，而不是只记住这个例外。

验证结果应当回到 overall structure ：新发现改变了哪个局部结构的职责，或者改变了哪些结构之间的关系？

质疑

质疑不是默认认为实现错误，而是追问设计约束：

  • 为什么采用当前顺序，而不是另一种顺序？

  • 为什么在这里回调、缓存、复制或异步执行？

  • 这是语言限制、兼容要求，还是业务权衡？

  • 当前实现是必要条件，还是一种可替换策略？

高级语言能够实现自举，不代表用该语言编写的框架天然可以自举。框架只有在构建或演进自身时复用了自身能力，才能讨论自托管或 Dogfooding ；局部抽象的递归复用也不等同于严格意义上的自举。

五、两种阅读路径

栈式：从整体递归到局部

“栈式”阅读是一种自顶向下的递归拆分：为了理解 overall structure ，进入一个关键 local structure ；理解该局部后，再返回上一层校正整体模型。

  1. 猜想整体： 明确框架实现什么，并列出可能的关键局部结构。

  2. 进入局部： 选择一个与当前问题最相关的结构阅读实现。

  3. 验证职责： 判断它实际接收什么、产生什么、依赖什么。

  4. 返回整体： 用阅读结果校正上一层结构图。

  5. 继续递归： 只在仍有关键问题无法解释时进入下一层。

链式：沿实际过程追踪

“链式”阅读关注多个 local structure 按时间或因果关系组成的执行路径：

入口 → 解析 → 转换 → 调度 → 执行 → 输出或副作用

阅读时重点关注：

  • 为什么某个步骤必须先发生，另一个步骤必须后发生？

  • 数据和控制权如何在结构之间转移？

  • 同步、异步、回调和重试在哪里改变了流程？

  • 失败后从哪里中断、回滚或恢复？

栈式阅读用于建立结构地图，链式阅读用于验证真实过程。两者交替使用，才能避免只有静态目录认知，或者只有零散调用细节。

六、系统化源码阅读流程

1. 明确阅读问题

先写下本次阅读需要回答的问题，例如“一个请求如何被路由”或“事务在什么位置提交”。没有具体问题时，阅读范围会无限扩张。

2. 建立外部模型

从文档、示例、公开 API 和最小测试开始，记录框架的输入、输出、配置、状态以及明确可观察的行为。

3. 绘制初始结构

找出入口、核心抽象、关键状态和扩展点，形成对 overall structure 的第一版猜想。不需要一开始就保证完整。

4. 选择一条主路径

使用一个真实场景贯穿源码。优先阅读正常主路径，再根据需要补充失败、并发和边界路径。

5. 逐段验证

每进入一个 local structure ，回答四个问题：

  1. 它解决什么局部问题？

  2. 它接收和产生什么信息？

  3. 它依赖哪些前置条件？

  4. 它如何影响下一步？

6. 回写整体模型

把验证结果更新到结构、流程和状态模型中。阅读笔记应记录“理解发生了什么变化”，而不只是复制代码。

7. 提炼设计判断

区分以下三类内容：

  • 事实： 当前代码实际做了什么。

  • 约束： 为什么必须这样做。

  • 策略： 当前选择了什么方案，是否存在替代实现。

只有完成这种区分，才能把源码阅读结果迁移到其他项目，而不是机械模仿当前实现。

七、常见误区

过早陷入细节

如果一个细节不能帮助回答当前问题，先记录它，再回到主路径。局部代码复杂不代表它对当前阅读目标重要。

按目录顺序阅读

目录结构反映代码组织方式，不一定反映运行过程。优先从公开入口、测试用例和关键调用链建立方向。

把类等同于抽象

抽象可能跨越多个类，也可能只是一个函数、协议或状态转换。不要用文件边界代替职责边界。

把现有实现视为最优解

源码只能证明当前系统选择了这种实现，不能证明它在所有约束下都是最优方案。理解历史、兼容性和取舍后，才能评价设计。

追求完全理解

大型框架不适合一次性完全理解。合理目标是围绕一个问题建立足够准确的局部模型，并明确尚未验证的部分。

八、阅读完成的判断

当能够完成以下内容时，一轮源码阅读可以暂时结束：

  • 用一句话说明框架或当前子系统解决的问题。

  • 说明输入如何经过关键结构形成输出或副作用。

  • 列出主路径上的关键 local structure 及其职责。

  • 指出主要状态、扩展点和失败边界。

  • 区分已经从源码验证的事实与仍然保留的猜想。

  • 总结至少一个可以迁移到其他场景的设计判断。

九、总结

编码能力的演进可以概括为：

使用语言 → 使用生态 → 提取抽象 → 理解语言与问题 → 构造可迭代生态

框架阅读的过程可以概括为：

建立整体 → 识别局部 → 追踪关系 → 验证过程 → 校正整体

两条路径最终指向同一件事：不只知道系统“怎么实现”，还能够解释它“为什么这样实现”、它依赖哪些条件，以及怎样让自己的理解和系统本身持续迭代。
