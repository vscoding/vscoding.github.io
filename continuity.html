Continuity

连续性不是没有变化，而是变化前后的状态仍然存在可说明、可验证的关系。

一、连续性讨论的是什么

一个系统会不断变化：程序被重构，接口被升级，数据被迁移，服务发生故障转移，组织中的人员也会更替。

变化本身并不等于断裂。判断一个过程是否具有连续性，需要回答四个问题：

  1. 什么在变化？ 是数据、结构、行为、语义，还是系统提供的能力？

  2. 变化如何发生？ 后继状态能否由前一状态、外部输入和明确的规则产生？

  3. 什么必须保持？ 是身份、约束、语义、接口契约，还是某种可观察行为？

  4. 什么构成断裂？ 是链路不可追溯、信息不可接受地丢失，还是关键不变量被破坏？

过程连续性是状态演化序列相对于给定观察对象、维度、时间尺度和允许损失所具有的性质：每个后继状态都有合法来源，该维度所需的信息能够向后传递，并且领域指定的不变量、语义或能力在变化中得到保持。

这个定义面向系统和软件工程，不等同于数学分析或拓扑学中的连续映射。数学连续性是其中一个可以使用的分析维度，而不是所有连续性概念的总定义。

这些维度不能互相代替：

  • Git 提交链完整，只能较强地说明因果连续，不能保证需求语义没有漂移；

  • 单个进程发生中断，但请求被副本接管，执行过程不连续，服务能力仍可保持运行连续；

  • 哈希结合可信的来源记录可以验证内容关联，却不能独立证明来源，也不能恢复原始内容，因此可追溯不等于可逆。

五、连续性的断裂与重建

断裂不是“发生了变化”，而是变化越过了当前观察维度允许的关系边界。发现断裂后通常有三种处理方式：

  1. 重建链路 ：利用日志、备份或数据血缘找回缺失的来源与中间状态；

  2. 建立桥梁 ：使用迁移、适配器或兼容层，在本来不兼容的新旧状态之间建立可验证的转换；

  3. 声明新起点 ：当原关系无法恢复或不值得维持时，明确终止旧链，并为新状态建立可信来源和新契约。

例如，数据库被直接修改后，可以根据审计记录重建迁移脚本；如果旧语义已经无法可靠恢复，就应把当前快照声明为新的基线，而不是伪造一条从未发生过的历史。

修复连续性不一定是恢复原状态，更常见的是补充转换关系，或者诚实地建立新起点。

为什么连续性不够

任何算法都可以表示成状态转移链，但这种表示没有说明状态编码长度、单步计算时间和总步骤数是否受输入规模的多项式约束。因此，链式执行、可逆性或数学连续性本身都不能推出 。

离散也不等于不连续。当定义域采用离散拓扑时，每一个从该空间出发的映射都是连续映射；大量属于 的问题同样具有离散状态空间。

把离散问题放宽为连续优化问题，是常见的算法方法。要由此证明某个 NP 完全判定问题属于 ，必须同时证明：

  1. 转换后的表示规模为多项式；

  2. 连续问题能以足够精度在多项式时间内求解；

  3. 连续解能在多项式时间内恢复为原问题的正确“是/否”答案；

  4. 整个过程对所有输入都成立，而不只是对特定实例有效。

如果讨论的是搜索问题，还需要额外证明能够在多项式时间内构造见证。连续松弛可能产生非整数解、精度问题或松弛间隙，“状态空间变得光滑”本身不是复杂度证明。

可以保留的有限类比

NP 证书可以类比为一种长度受多项式约束、可以高效检查的有限证明。但 不等价于“所有非构造证明都有构造表达”，也不直接涉及哥德尔不完全性。

对于 SAT 等具有自归约性质的问题，如果已有多项式时间判定算法，通常可以通过逐步固定变量并重复询问可满足性来构造见证。这里起作用的是判定算法的时间界与问题结构，而不是证明路径的连续性。

连续性在这里最多提供一种启发：局部可验证的信息不一定包含通向全局解的有效方向。它不能作为关于 与 的数学推论。

九、连续性的限度

连续性依赖观察尺度

进程重启可能是进程轨迹的断裂，却不一定是服务能力的断裂；一次破坏性 API 升级可能终止旧契约，却建立了更清晰的新契约。

讨论连续性之前，必须说明观察对象、时间尺度和需要保持的关系。脱离这些条件，“系统是连续的”不是一个完整命题。

连续性会传播错误

连续性并不天然代表正确。如果错误的约束、数据或组织习惯被完整继承，连续性反而会让问题长期存在。技术债往往就是一种高度连续的错误积累。

因此，需要区分：

  • 应被保持的不变量；

  • 可以演化的实现细节；

  • 必须主动终止的错误传统。

断裂有时是必要的

重置、分叉、破坏性升级和重新设计并不总是失败。当旧状态无法满足新目标，或者维持兼容性的成本超过收益时，主动制造边界可能比伪装连续更诚实。

关键不在于避免一切断裂，而在于让断裂具备：

  • 明确原因；

  • 可识别边界；

  • 可迁移路径；

  • 可验证的新起点。

十、判断连续性的检查表

分析一个系统或过程时，可以依次回答：

  1. 状态是什么？ 哪些内容属于被观察的系统？

  2. 转移是什么？ 新状态由哪些规则、输入和上下文产生？

  3. 来源能否追溯？ 能否解释每个关键状态从何而来？

  4. 什么必须保持？ 身份、信息、语义、接口还是运行能力？

  5. 如何验证保持关系？ 使用不变量、等价测试、审计还是恢复演练？

  6. 允许丢失什么？ 哪些信息可以被压缩、遗忘或替换？

  7. 什么构成断裂？ 边界是否可被观测和判断？

  8. 断裂后如何处理？ 恢复原链、建立适配层，还是声明新起点？

  9. 局部与整体是否一致？ 每一步合法是否真的导向最终目标？

总结

连续性不是某个孤立状态的属性，而是状态序列在特定观察维度下呈现出的关系。

它不要求一切保持不变，而要求我们明确：变化从哪里来、通过什么规则发生、哪些内容必须被继承，以及何时应当承认已经出现断裂。

对于开发者而言，连续性的价值在于把“不要破坏系统”这种模糊要求，转化为可以设计、验证和权衡的约束：

连续性不是拒绝变化，而是让变化仍然能够被理解。
