Node.js + TypeScript 工程化

记录日常 Node.js + TypeScript 项目开发中常用的目录结构、工具链与工程规范。示例使用 pnpm ，也可以按团队习惯替换为 npm 或 yarn。

工程化目标

工程化不是简单地堆叠工具，而是通过统一约定降低协作和维护成本：

  • 环境一致 ：固定 Node.js 与包管理器版本，减少“在我的机器上可以运行”的问题。

  • 类型安全 ：使用 TypeScript 提前发现类型错误，并明确源码与构建产物的边界。

  • 代码一致 ：使用 ESLint、Prettier 和 EditorConfig 统一检查与格式化规则。

  • 流程可重复 ：将开发、构建、检查和测试等操作收敛到 package.json 脚本中。

  • 配置可管理 ：区分不同环境的配置，不将密钥提交到代码仓库。

环境与版本

建议使用 nvm、 fnm 或 Volta 管理 Node.js 版本，并在项目根目录通过 .nvmrc 固定版本：

24

通过 package.json 声明运行时和包管理器要求：

{ "engines": { "node": ">=24" }, "packageManager": "pnpm@10.0.0" }

开启 Corepack 后，团队成员可以使用项目声明的包管理器版本：

corepack enable pnpm install

版本号应根据项目实际运行环境调整；生产环境、CI 和本地开发应尽量保持一致。

初始化项目

mkdir node-typescript-app cd node-typescript-app pnpm init pnpm add -D typescript tsx @types/node pnpm exec tsc --init

  • typescript ：提供类型检查器和 TypeScript 编译器 tsc。

  • tsx ：开发阶段直接运行 TypeScript，适合本地启动和脚本执行。

  • @types/node ：提供 Node.js 内置模块和全局变量的类型定义。

推荐目录结构

project-root/ ├── src/ │ ├── config/ # 配置读取与校验 │ ├── modules/ # 按业务领域组织的模块 │ ├── shared/ # 跨模块复用的代码 │ └── index.ts # 应用入口 ├── tests/ # 自动化测试 ├── scripts/ # 构建、迁移等辅助脚本 ├── dist/ # 编译产物，不提交到仓库 ├── .env.example # 环境变量示例 ├── .editorconfig ├── .gitignore ├── .nvmrc ├── .prettierignore ├── .prettierrc.json ├── eslint.config.js ├── package.json ├── pnpm-lock.yaml ├── tsconfig.json └── README.md

目录结构应服务于项目规模。小型项目不必提前创建所有目录；当职责真正出现时再拆分，避免只有一两个文件却形成过深的目录层级。

TypeScript 配置

以下配置适合以现代 Node.js ESM 方式运行的项目：

{ "compilerOptions": { "target": "ES2022", "module": "NodeNext", "moduleResolution": "NodeNext", "rootDir": "src", "outDir": "dist", "strict": true, "noUncheckedIndexedAccess": true, "exactOptionalPropertyTypes": true, "esModuleInterop": true, "forceConsistentCasingInFileNames": true, "skipLibCheck": true, "sourceMap": true }, "include": [ "src/**/*.ts" ], "exclude": [ "node_modules", "dist" ] }

同时在 package.json 中设置 "type": "module" 。采用 NodeNext 时，本地模块的导入路径需要遵循 Node.js ESM 规则：

import {loadConfig} from './config/index.js'

虽然源码是 .ts 文件，导入路径仍写 .js ，因为编译后由 Node.js 加载的是 JavaScript 文件。如果项目使用 CommonJS，应统一调整 module、 moduleResolution 和 package.json ，不要混用两套模块规范。

依赖与脚本

业务运行必需的包放入 dependencies ，只在开发、构建或测试阶段使用的工具放入 devDependencies 。锁文件应提交到代码仓库，以保证安装结果可重复。

将团队日常命令统一定义在 package.json 中：

{ "type": "module", "scripts": { "dev": "tsx watch src/index.ts", "build": "tsc -p tsconfig.json", "start": "node dist/index.js", "typecheck": "tsc -p tsconfig.json --noEmit", "lint": "eslint .", "lint:fix": "eslint . --fix", "format": "prettier . --write", "format:check": "prettier . --check", "check": "pnpm typecheck && pnpm lint && pnpm format:check" } }

脚本名称尽量表达职责，而不是实现细节。CI 与本地都调用相同脚本，避免维护两套检查逻辑。

ESLint 与 Prettier

安装代码检查和格式化工具：

pnpm add -D eslint @eslint/js typescript-eslint \ prettier eslint-config-prettier

eslint.config.js 使用 ESLint Flat Config：

import eslint from '@eslint/js' import prettier from 'eslint-config-prettier' import tseslint from 'typescript-eslint' export default tseslint.config( { ignores: ['dist/**', 'coverage/**'], }, eslint.configs.recommended, ...tseslint.configs.recommended, prettier, )

.prettierrc.json 只保留团队明确需要的格式约定：

{ "semi": false, "singleQuote": true, "trailingComma": "all" }

ESLint 负责发现潜在代码问题，Prettier 负责代码排版。 eslint-config-prettier 用于关闭两者之间可能冲突的格式规则。

EditorConfig

.editorconfig 为不同编辑器提供基础格式约定：

root = true [*] charset = utf-8 end_of_line = lf insert_final_newline = true indent_style = space indent_size = 2 trim_trailing_whitespace = true [*.md] trim_trailing_whitespace = false

EditorConfig 只解决基础编辑行为，不能替代 ESLint 和 Prettier。

环境变量

本地配置写入 .env ，并将 .env 加入 .gitignore 。仓库只提交不包含真实密钥的 .env.example：

NODE_ENV=development PORT=3000 DATABASE_URL=postgresql://user:password@localhost:5432/app

应用启动时应集中读取并校验环境变量，避免在业务代码中到处访问 process.env 。缺少必填配置时应尽早失败，而不是运行到具体请求时才报错。

Git 忽略规则

node_modules/ dist/ coverage/ .env .env.* !.env.example *.log .DS_Store

不要忽略包管理器锁文件。对于应用项目，锁文件是保证本地、CI 与生产安装结果一致的重要组成部分。

日常开发流程

# 安装依赖 pnpm install # 启动开发环境 pnpm dev # 提交前执行完整检查 pnpm check # 构建并运行编译产物 pnpm build pnpm start

推荐在持续集成中至少执行以下步骤：

  1. 使用锁文件安装依赖： pnpm install --frozen-lockfile。

  2. 执行类型检查、ESLint 和格式检查： pnpm check。

  3. 执行自动化测试（项目引入测试框架后）。

  4. 执行生产构建： pnpm build。

工程化检查清单

  • Node.js 和包管理器版本已明确。

  • 锁文件已提交，CI 使用冻结锁文件安装依赖。

  • TypeScript 已开启严格模式，源码和构建产物目录已分离。

  • ESM 或 CommonJS 已统一选型，没有混用模块规范。

  • 开发、检查、测试、构建和启动命令已收敛为项目脚本。

  • ESLint、Prettier 与 EditorConfig 职责清晰且规则不冲突。

  • 环境变量有示例文件，真实密钥不会进入代码仓库。

  • 提交前检查与 CI 使用相同命令。
