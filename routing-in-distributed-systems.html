Routing in Distributed Systems

分布式系统中的路由（Routing）是指根据请求的目标、数据分布及集群状态，将请求发送到合适的服务节点或数据分片。核心问题不是“由客户端还是服务端负责”，而是 路由决策在哪里完成、路由元数据由谁维护，以及拓扑变化后如何恢复正确路由。

路由模型

客户端路由（Client-side Routing）

客户端根据分片规则或集群元数据，直接选择目标节点。典型流程为：

  1. 从服务端获取分区与节点的映射关系。

  2. 根据 Key、分区标识或其他路由键确定目标。

  3. 直接向目标节点发送请求。

  4. 遇到重定向或元数据过期时，刷新映射并按规则重试。

优势： 减少代理转发和额外网络跳数，适合高吞吐、低延迟场景。

代价： 客户端或 SDK 需要处理拓扑变化、路由缓存、重试及故障恢复。不同语言的客户端实现也需要保持一致。

Kafka Producer、Redis Cluster 的集群感知客户端都具有客户端路由的特征。

服务端路由（Server-side Routing）

客户端连接固定入口，由代理、协调节点或网关查询路由信息，再将请求转发或分发给后端节点。

优势： 客户端无需感知具体的数据分布；路由逻辑可以在服务端集中维护和更新。

代价： 入口层引入额外处理与网络开销，需要考虑水平扩展、高可用、热点、连接管理与故障切换。

MongoDB 分片集群的 mongos 、Elasticsearch 的协调节点属于此类；但它们的职责不仅限于简单转发，还可能包含查询拆分、结果汇总等操作。

两种模式并非互斥

实际系统通常采用混合模式：客户端负责选择入口或分区，服务端再完成内部路由。例如，客户端可使用服务发现或负载均衡选择接入节点，再由该节点定位数据分片。

需要区分三个概念：

  • 服务发现： 找到可连接的服务实例。

  • 负载均衡： 在满足条件的实例之间分配流量。

  • 数据路由： 根据数据归属或分区规则定位目标节点。

三者可以组合，但不能互相替代。

客户端路由系统示例

以下系统的客户端具备分区计算或路由元数据感知能力，可以直接访问负责目标数据的节点。这里讨论的是 数据请求的路由决策 ，不等同于最初的服务发现过程。

Kafka Producer

Kafka Producer 从 Broker 获取 Topic、Partition 与 Leader 元数据：

  1. 根据显式指定的 Partition、Key 分区策略或默认分区器确定目标 Partition。

  2. 从缓存的集群元数据中查找该 Partition 的 Leader Broker。

  3. 直接向 Leader Broker 发送生产请求。

  4. Leader 发生变化或元数据失效时，更新元数据并按客户端策略重试。

路由特点： 客户端同时负责“选择 Partition”和“定位 Leader”。Key 不一定参与分区计算；无 Key、指定 Partition 以及自定义分区器均可能改变选择结果。

Redis Cluster

集群感知客户端获取 Slot 与主节点映射，根据 Key 的 CRC16 结果（包含 Hash Tag 规则）计算 Slot，然后直接连接目标主节点。

  • MOVED 表示应前往新的 Slot 负责人，并更新或刷新映射。

  • ASK 通常出现在迁移期间，只对当前请求临时重定向，目标节点需先接收 ASKING。

  • 节点间传播元数据，客户端通过缓存与重定向共同应对拓扑变化。

路由特点： 客户端负责正常路径的定位，Redis 节点提供纠错反馈。具体 Slot 管理与迁移过程见下文“Redis Cluster 的 Hash Slot 机制”。

Apache Cassandra

Cassandra 使用分区键计算 Token，并将 Token 范围分配给节点。支持 Token-aware Routing 的驱动可基于集群元数据选择负责该分区的副本作为协调节点。

  • 客户端维护 Token、节点与副本分布信息。

  • 分区键已知时，驱动可优先选择合适的副本，减少非必要的节点间转发。

  • 接收请求的协调节点仍负责满足一致性级别所需的副本读写与结果协调。

路由特点： 客户端优化协调节点的选择，但不是绕过 Cassandra 的服务端副本协调机制。

Couchbase SDK

Couchbase 的集群感知 SDK 获取 Bucket 的分区映射，将文档 Key 映射到 vBucket，再定位负责该 vBucket 的节点。

  • 正常情况下 SDK 可将 Key-Value 操作直接发往目标节点。

  • 集群重平衡或故障转移后，客户端更新配置映射并重试适用的操作。

路由特点： 借助固定数量的逻辑分区（vBucket），将客户端的 Key 定位与物理节点调整解耦；此处主要指 Key-Value 数据操作，查询服务有其独立路由方式。

Apache HBase

HBase 原生客户端通过集群元数据定位 Row Key 所在的 Region，缓存 Region 到 RegionServer 的映射，然后直接向目标 RegionServer 发送读写 RPC。

  • Region 发生迁移或拆分时，客户端在定位失败后刷新缓存并重试。

  • RegionServer 执行读写，但通常不是替其他 Region 进行统一转发的代理入口。

  • 使用 REST 或 Thrift Gateway 时，客户端到网关的访问形态不同，不能与原生客户端路由混为一谈。

路由特点： 默认是客户端感知 Region 位置的直连模式，而非典型服务端代理路由。

服务端路由系统示例

以下系统通常由代理、协调节点或服务入口决定内部请求路径。客户端无需自行维护完整的数据分片归属关系，但服务端入口必须能应对拓扑变更和负载压力。

MongoDB Sharded Cluster

应用连接 mongos ，由 mongos 根据分片元数据确定需要访问的 Shard：

  • 查询携带可用于定向的分片键条件时，尽可能仅访问相关 Shard。

  • 无法准确限定目标时，可能向多个 Shard 分发查询（scatter-gather）。

  • mongos 可能负责合并与整理各 Shard 返回的结果。

路由特点： 分片定位及跨分片请求协调集中在 mongos ，应用无需维护 Chunk 到 Shard 的映射。

Elasticsearch

客户端将搜索请求交给可接收请求的 Elasticsearch 节点。充当协调节点的节点根据集群状态与 Shard 路由信息，执行分发和结果归并。

  • 查询阶段将请求发送到相关 Shard 的适当副本。

  • 协调节点整理各 Shard 的结果，必要时执行后续获取阶段。

  • 普通数据节点也可以承担协调职责；专用协调节点是部署选项，不是必需条件。

路由特点： 请求入口负责分片扇出与结果合并，尤其需要关注搜索聚合的内存开销及跨 Shard 请求成本。

TiDB

应用通过 MySQL 协议连接 TiDB SQL 节点，SQL 层解析和优化查询后，根据 Region 分布信息访问 TiKV 等执行组件。

  • TiDB 从 PD 等组件获取和缓存 Region 路由元数据。

  • 查询可拆分为分布式任务，发送到对应 Region 或计算节点。

  • Region 分裂、迁移或 Leader 变化时，内部组件刷新路由并执行相应重试。

路由特点： 应用感知的是 SQL 接入地址，而数据分布、任务调度与 Region 定位由服务端体系处理。

Redis Cluster 的 Hash Slot 机制

Key 如何映射到 Slot

Redis Cluster 将 Key 空间划分为 16,384 个 Hash Slot ，编号为 0～16383 。一般情况下：

slot = CRC16(key) mod 16384

如果 Key 包含合法的 Hash Tag（例如 user:{42}:profile ），则仅对花括号内的 42 计算 CRC16。Hash Tag 能使多个 Key 落入同一 Slot，便于满足部分多 Key 命令的同槽要求。

Slot 是逻辑分区，而非物理节点。 一个主节点通常负责多个 Slot；增加节点时可以迁移部分 Slot，而不需要改变 Slot 总数。

Slot 如何分配给主节点

创建集群时，可通过 redis-cli --cluster create 等工具分配 Slot；扩容时可通过重新分片调整归属。例如，三个主节点的初始分布可以是：

副本节点用于高可用，不作为正常情况下的 Slot 主负责人。发生故障转移后，提升为主节点的副本可以接管原主节点负责的 Slot。

Slot 元数据如何维护

每个 Redis Cluster 节点维护集群视图，包括节点标识、地址、角色、健康状态、配置纪元（config epoch）和 Slot 归属信息。客户端可通过 CLUSTER SHARDS （较新版本推荐）或 CLUSTER SLOTS 获取路由元数据。

这里应将 逻辑数据结构与 Redis 具体版本的 C 语言内部结构区分开：实现并非简单的 struct clusterNode { int slots[16384]; } 。其内部编码和表示会随版本演进，不宜使用未经核实的伪结构体说明源码实现。

节点如何传播集群状态

集群节点通过 Cluster Bus 交换 PING/PONG 等消息，传播成员关系、故障判断和 Slot 配置等信息。配置纪元用于比较冲突的 Slot 归属声明，帮助集群在拓扑变化后收敛。

注意： Gossip 是异步传播机制，不保证所有节点在任意时刻都有完全一致的瞬时视图。客户端必须能够处理路由过期与重定向。

客户端如何定位与重试

  1. 客户端获取 Slot 到节点的映射。

  2. 根据 Key 计算 Slot，并将命令发送到相应节点。

  3. 若节点返回 MOVED ，客户端应将请求重发至提示的目标节点，并刷新或修正 Slot 映射。

  4. 若节点返回 ASK ，通常表示 Slot 正在迁移；客户端仅对这一次重定向，在目标节点发送 ASKING 后再执行原命令， 不能仅凭 ASK 永久修改映射。

Client ──(key → slot)──> Node A │ │ │<──── MOVED slot B ────┤ Slot 已由 B 负责 └──────────────────────> Node B Client ──────────────────> Node A │<──── ASK slot B ──────┤ Slot 迁移中 └──> Node B: ASKING → 原命令

重试还应考虑超时、幂等性和最大重试次数，避免因网络故障造成无限重试或重复执行。

Slot 如何迁移（Resharding）

将某个 Slot 从 A 迁移到 B 的典型过程如下：

  1. 将 B 的目标 Slot 设置为 IMPORTING ，将 A 的该 Slot 设置为 MIGRATING。

  2. 使用集群管理工具（例如 redis-cli --cluster reshard ）迁移属于该 Slot 的 Key；底层可使用 MIGRATE。

  3. 迁移过程中，A 仍可能处理尚未迁移的 Key，对需要访问 B 的请求返回 ASK。

  4. 完成数据迁移后，更新 Slot 的正式归属并传播新的集群配置；旧路由可能收到 MOVED。

这是便于理解的流程摘要；实际迁移会涉及状态切换、错误处理和多 Key 命令限制，生产环境优先使用成熟的集群管理工具。

如何检查集群路由

# 查看 Slot 到主节点及副本的映射（较新版本） redis-cli -h 127.0.0.1 -p 6379 CLUSTER SHARDS # 兼容性较好的 Slot 范围查询 redis-cli -h 127.0.0.1 -p 6379 CLUSTER SLOTS # 查看集群节点、角色和 Slot 标记 redis-cli -h 127.0.0.1 -p 6379 CLUSTER NODES # 查询指定 Key 对应的 Slot redis-cli -h 127.0.0.1 -p 6379 CLUSTER KEYSLOT 'user:{42}:profile' # -c 开启 redis-cli 的集群重定向处理 redis-cli -c -h 127.0.0.1 -p 6379

选型时重点评估：

  1. 延迟与吞吐： 是否需要尽量减少请求转发层。

  2. 客户端可控性： 是否能统一维护不同语言的 SDK 和路由协议。

  3. 拓扑变化： 扩缩容、主从切换时元数据如何失效、刷新与收敛。

  4. 故障处理： 超时、重定向、重试和幂等性是否有明确约束。

  5. 观测性： 路由命中率、重定向次数、元数据刷新、跨分片请求与入口层负载是否可度量。

结论： 客户端路由并不天然优于服务端路由，服务端路由也不一定意味着单点瓶颈。关键是把 数据定位、拓扑维护、请求转发和故障恢复 作为一套完整协议来设计，而不是仅比较一次请求是否多经过一个节点。
