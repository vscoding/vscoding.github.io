Trigger Keyword

触发器关键词用于在提交信息、Pull Request 评论、Issue 评论或其他自动化入口中，显式声明要执行的 CI 动作。

关键词本身应该保持稳定、可读、可检索，并且尽量只表达“要触发什么任务”。分支、提交号、运行人、运行时间等上下文信息不应该编码进关键词里。

基本格式

:ci:<domain>:<action> :ci:<domain>:<action>:<target> :ci:<domain>:<action>:<target>:<option>[,<option>...]

示例：

:ci:img:build:elasticsearch:variant=bitnami :ci:img:sync:languages:arch=amd64 :ci:ops:cleanup:runs :ci:shell:test

字段说明

字段

是否必填

说明

示例

:ci:

是

固定前缀，用于和普通文本区分。

:ci:

<domain>

是

任务域，表示触发哪一类自动化能力。

img、 ops、 shell

<action>

是

动作，表示对目标执行什么操作。

build、 sync、 cleanup、 test

<target>

条件必填

目标，表示具体作用对象。镜像、运维类任务必须填写；单例动作可以省略。

nginx-ext、 postgres、 runs

<option>

否

选项，用于表达目标的变体、架构等附加维度。有选项时必须先有 target。

variant=bitnami、 arch=amd64

设计原则

  1. 固定前缀 所有 CI 触发关键词都以 :ci: 开头，避免和普通描述文本、版本号、镜像名混淆。

  2. 短域名，强约束 <domain> 应使用少量稳定缩写，而不是自由文本。这样便于解析器做白名单校验，也便于后续维护。

  3. 动作使用动词 <action> 表示动作，不承载目标含义。比如构建镜像统一使用 build ，同步镜像统一使用 sync ，不要混用 rebuild、 mirror、 copy 等近义词。

  4. 目标表达业务对象 <target> 应表达被操作的对象，例如 nginx-ext、 oracle19、 teamcity-server 。不要把架构、变体、环境等维度硬塞进目标名。对于唯一目标的单例动作可以省略 target ，例如 :ci:shell:test。

  5. 变化维度放到选项 架构、变体、渠道等可选维度放到最后的 k=v 选项里，例如 arch=amd64、 variant=bitnami。

  6. 一个关键词只触发一个意图 不要设计“顺手做多件事”的关键词。需要多个任务时，写多个关键词，让编排逻辑显式处理依赖关系。

命名规范

通用规范

  • 统一使用小写字母。

  • 单词分隔使用 - ，例如 gitea-runner、 mkdocs-builder。

  • 允许在目标名中保留上游项目自身的点号，例如 rocket.chat。

  • 避免空格、斜杠、中文、大小写混用。

  • 关键词不要带引号；如果写在配置文件中需要引号，由配置格式负责。

action

选项设计

选项只用于表达附加维度，不应该改变核心动作语义。

:ci:<domain>:<action>:<target>:k=v[,k=v...]

有选项时必须保留 <target> ，避免把 k=v 误解析成目标名。

推荐选项：

option

含义

示例

variant

目标变体

variant=bitnami

arch

CPU 架构

arch=amd64、 arch=arm64

channel

发布或同步渠道

channel=stable

version

明确版本

version=19

多选项按稳定顺序书写，优先级建议为：

variant -> arch -> channel -> version

示例：

:ci:img:build:elasticsearch:variant=bitnami :ci:img:sync:languages:arch=amd64 :ci:img:sync:languages:arch=arm64

匹配规则建议

  • 解析时按完整 token 匹配，不做子串匹配。

  • 推荐一行一个关键词，降低人工阅读和解析复杂度。

  • 评论或提交信息中可以出现多个关键词，触发器应逐个去重后执行。

  • 对未知 domain 、未知 action 、非法选项要直接拒绝，不要静默忽略。

  • 对同一个关键词重复出现的情况，默认按一次处理。
